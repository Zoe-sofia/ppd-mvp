## 1. 运行方式

零依赖、无构建、无框架、无 CDN：所有资源都在本目录内，浏览器直接加载 ES modules。

```bash
# 方式一：任意静态服务器（推荐）
npm start                 # 等价于 python -m http.server 8099
# 打开 http://127.0.0.1:8099/index.html

# 方式二：Node
npm run serve:node        # 等价于 npx serve . -l 8099
```

**不要双击 `index.html`。** 浏览器对 `file://` 下的 ES module 有 CORS 限制，页面会白屏；
必须通过 http 打开（任意静态服务器均可）。

首次打开会自动生成"中等场景"演示数据，之后所有改动保存在浏览器 localStorage
（键名 `ppd-mvp-v1`），刷新不丢。右上角可备份/恢复 JSON、切换三套场景。

浏览器要求：Chrome / Edge 90+、Firefox 113+、Safari 16.4+。
`.xlsx` 导入用到原生 `DecompressionStream`（不支持的浏览器会提示改用 CSV 或 `.xls`）；
`.xls` 与 CSV（含 GBK）不依赖该 API。

`package.json` 里没有任何依赖，仅用于两件事：声明 `"type": "module"` 让 Node 能直接运行测试，
以及提供 `start` / `test` / `check` 三个脚本入口。

### 1.1 在线访问与 GitHub Pages 部署

**在线地址**：<https://zoe-sofia.github.io/ppd-mvp/> —— 打开即用，不需要本机起任何服务，
也不依赖任何后台进程（本机的 `python -m http.server` 只是开发时可选的自测方式）。

本项目从设计上就是"纯静态 + 无后端"，能否离线部署只取决于三件事，三者都已落实：

| 依赖项 | 现状 | 说明 |
|---|---|---|
| 资源路径 | **全部相对路径**（`./assets/...`） | Pages 的项目站点挂在 `/<repo>/` 子路径下，`/assets/...` 这类根路径引用必然 404 |
| 路由 | **hash 路由**（`#/dashboard`） | 刷新、直链、前进后退都不需要服务端 rewrite；未知 hash 回退到工作台而不是白屏 |
| 接口 / 后端 | **无** | 没有 `fetch`、XHR、WebSocket、Service Worker；数据只在浏览器 localStorage 与本地文件之间流转 |

配套的部署设施：

| 文件 | 作用 |
|---|---|
| `.github/workflows/pages.yml` | push 到 `main` 自动构建并发布 `app/`；发布前校验必需文件、并**拦截 `src="/..."` 这类根路径引用**（一上线就白屏的头号原因） |
| `app/.nojekyll` | 关闭 Jekyll 处理，避免 `_` 开头的文件/目录被丢弃 |
| `app/404.html` | 未知路径回退说明页（带在线地址与本地预览命令），不再返回裸 404 |
| `app/index.html` 里的 `file://` 兜底 | 双击打开时明确提示"请通过网址访问"，而不是给一片白屏 |

发布产物只包含 `index.html` / `404.html` / `.nojekyll` / `assets/`，
测试夹具、`package.json` 与设计文档不进入公开站点。

> 若把站点部署到**自己的域名或子路径**（如 `https://example.com/pmc/`），只需保证整个 `app/`
> 目录原样放到该路径下即可 —— 代码里没有任何写死的 origin，也没有绝对路径。
> 唯一的例外是 `index.html` 里的 `og:image` / `canonical` 与 `404.html` 里的在线地址，
> 它们只影响分享卡片，不影响功能，按需替换即可。

### 1.2 在线演示的数据归属：每人一份，不共享

用在线地址（或本机 http 地址）做着测，很容易问一句"我导入的测试数据别人会看到吗？会不会互相干扰？"
答案是**不会**，而且这不是配置问题，是架构决定：

| 问题 | 答案 |
|---|---|
| 多人打开同一个在线地址，看到的是同一份数据吗 | **不是。** 各自浏览器 `localStorage` 互相独立 |
| 我导入的 Excel 别人能看到吗 | 不能。数据从未离开本机浏览器，页面上也没有任何请求把它发出去 |
| 换一台电脑 / 换一个浏览器 / 开无痕窗口 | 都是**全新的空库**，首次打开自动生成演示数据 |
| 我清空数据会影响别人吗 | 不会，只清自己浏览器里的那一份 |
| 仓库里有没有"测试导入数据" | 没有。`tests/fixtures/` 是**测试样本文件**（xlsx / xls / GBK-CSV），只在跑 `npm test` 时被读，不参与站点运行，也不会写进任何人的浏览器 |

原因：GitHub Pages 只托管**静态文件**，没有数据库、没有接口、没有账号体系；浏览器同源策略也不允许
一个站点读写另一个站点的 `localStorage`。所以「在线演示」本质是一份**本机沙盒** —— 随便导、随便改、
随便清空，不影响他人、不污染仓库。

需要**多人共用同一份数据**时，当前只有两条路（都超出本 MVP 范围，见 §8）：

1. **整库文件传递**：一方「备份」导出 JSON，另一方「恢复」导入（整库替换，见 §5.3）。
   也可把 JSON 放进仓库让对方下载后导入，适合交接、复现问题、递交测评样本。
2. **接后端**：把 `core/store.js` 的 `load/save` 换成接口调用即可，`core/` 的规则层无需改动
   （分层纪律见 §2）；届时才需要账号、权限与并发控制。

> 一句话记法：**数据跟着浏览器走，不跟着网址走。**

## 3. 关键规则如何落地

**排产（§4.4）**
- 硬约束先行：HC-01 工序顺序、HC-02 工作中心能力、HC-03 不可生产日期、
  HC-04 日产能超限、HC-05 下游数量超上游。存在硬约束时"确认计划"按钮被禁用。
- 产能按**物理量**占用：件/日模式按件数，工时/件模式按标准工时换算成工时，
  再与当日可用工时比较（`capacityPoolOf` / `capacityDemandOf`）。
  同一工作中心常承接标准工时不同的多道工序，若一律按"件"占用，会排出
  "账面不超产能、实际超工时"的计划；排产与 HC-04 校验共用这一对函数，
  因此两处结论始终一致。HC-04 按 (工作中心, 日期) 汇总后只报一条，
  结果与任务数组顺序无关。
- 软约束只提示不拦截：交期紧张、负荷不均、缓冲不足、未确认到料、到料晚于计划开工。
- 评分：九因素归入 交付 / 物料 / 产能 三桶加权（三套策略 60/20/20、25/60/15、30/20/50），
  再按优先级贪心逐日占用产能，**不承诺全局最优**（界面已明示）。
- 可复现：排产本身不含随机数与当前时间，同一输入两次排产结果一致。

**齐套（§4.3）**
- 两级 BOM 展开（产品 → 半成品/物料 → 原材料）。
- 五态：齐套 / 部分齐套 / 缺料 / 可齐套（待到货）/ 到货风险；整单按最差项（短板原则）判定。
- 可用库存 = 库存 − 其他订单已确认预留，确认预留时界面会提示对其他订单的影响。

#### 3.1 齐套日：按日期累计，不按合计

这是本轮修正的核心口径。`kittingOf()` 不再用"确认到货合计够不够"，而是**逐日累计求首次达需日**：

```
① 库存 + 预计到货日 ≤ d 的已确认到货  →  截至 d 的可用量（availabilityCurve）
② 找最小的 d 使得 可用量(d) ≥ 需求量    →  该物料的 readyDate（firstMetDate）
   · 库存本身已够 → readyDate = ''（不需要等到货）
   · 永远不够     → readyDate = ''（不可知，不编日期）
③ 对整单所有缺料物料的 readyDate 取最大值 → orderReadyDate（整单齐套日）
   · 任一缺料物料 readyDate 为空 → orderReadyDate = ''（不可知）
④ 状态判定：
   gap = 0                        → 齐套
   readyDate ≤ 计划开工日          → 可齐套（待到货）
   readyDate > 计划开工日          → 到货风险
   未排产（planStart 空）          → 可齐套（及时性待排产后判断，不误报风险）
   stock>0 或 已确认到货>0         → 部分齐套
   否则                            → 缺料
```

旧实现的两个坑，用八张订单（TA-PO-001~008）钉死在 `tests/rules.test.mjs` 里：

| 订单 | 构造 | 旧口径错在哪 | 现行结论 |
|---|---|---|---|
| 001 | 40@+1、40@+5，需求 70，开工 +3 | 合计 80≥70 且首批 +1 早于开工 → 误判"可齐套" | 到货风险，达需日 +5 |
| 004 | 24@+10，开工 +2 | 只看到货数量够 → 误判"可齐套" | 到货风险，达需日 +10 |
| 006 | 无库存无到货 | 齐套日容易变成 `undefined` 或 `''` 混进比较 | 缺料，整单齐套日 `''` |
| 008 | 16@+2、16@+7，需求 32，开工 +4 | 只看首批 +2 → 误判"可齐套" | 到货风险，达需日 +7 |

`materialReadyDate(order, db)` 与 `kittingOf().orderReadyDate` 走同一套逻辑，两者结论必定一致
（同一物料清单、同一累计曲线），避免"页面上写一个日期、异常里写另一个"。

#### 3.2 半成品的两种口径（不要混用）

半成品（`type: SEMI`）在不同场景下要回答不同问题，所以有两条路径，**需求数量口径完全一致**：

| 函数 | 用途 | 半成品有下级 BOM 时 | 半成品无下级 BOM 时 |
|---|---|---|---|
| `explodeBom(productId, qty, db)` | **算需求**（齐套、异常、开工闸门） | 只展开下级材料，半成品自身**不计需求** | 按物料计需求（视同外购件） |
| `explodeBomTree(productId, qty, db)` | **展示需求明细**（物料页） | 保留半成品行 + 下级材料缩进，`kind='SEMI'` | 保留半成品行，`note` 标注"无下级 BOM" |

为什么算需求时不计半成品：自制件不该被"采购"，把它计进缺料会凭空多出一堆永远不买的缺料项。
为什么展示时仍要保留：`SE-GEAR` 这类半成品**有库存、有到货**（库存/到货页必须能看到它），
且要看懂"这批钢材是为哪个半成品备的"，否则明细里只有一堆散料，PMC 无法判断是不是漏了半成品。

`explodeBomTree()` 每行字段：`level` / `indent`（缩进层级）/ `parentId` / `parentCode` / `parentRequired` /
`childCount` / `semi` / `note`，渲染为 `└─` 缩进 + "所属"列 + 层级徽标（半成品 · 展开下级 / 二级（N 个下级）/ 一级）。

#### 3.3 销售行 ↔ 生产订单：双源关联

一张销售行可能拆成多张生产订单（一拆多），也可能多行合并成一张（多对一），因此关联存两处：

| 位置 | 作用 |
|---|---|
| `productionOrders.salesOrderLineId` | 单值出处，用于**回查交期**（`dueDateOf`）与旧数据兼容 |
| `orderLinks[]` = `{id, orderId, lineId, qty}` | 关联表，一张销售行可挂**多张**生产订单，并记录分配数量 |

导入生产订单时**两者同时写入**。此前只写了 `salesOrderLineId`，销售订单页的"生产订单"列
按 `orderLinks` 查不到任何记录，于是明明已经建过生产订单，却仍显示"建立生产订单"——
属于典型的"数据在，视图不认"。现在 `ordersOfLine()` 合并两个来源去重，
列为订单号徽标（`title` 显示状态），重复导入被拒绝时也不会重复建关联。

#### 3.4 物料预留：确认即扣减，可取消

- 每行给出建议预留量 `suggestQty`、已确认 `confirmed`、本次扣减 `deductNow`、
  物料总库存 `stockTotal`、扣减前后"其他订单可用" `availableBefore` / `availableAfter`。
- **确认预留**后，该数量从"其他订单可分配库存"中扣除，提示写明
  `已确认预留 A 12、B 5，合计扣减 17；N 张其他订单的可分配库存相应减少`。
- 未确认时表格明确显示"建议预留（未确认）"，不假装已占用。
- 支持**取消确认**：释放对应可用库存，提示写明释放量；支持"确认全部建议 / 取消本单全部预留"。
- 可用量口径始终是 `库存 − 其他订单已确认预留`（`allocatableStock`），所以扣减不需要改库存数字，
  取消也不需要"加回来"——只改预留记录，天然不会算重或算漏。

#### 3.5 筛选与排序的统一约定

十个页面里凡是有表格的地方，都遵循同一套交互，避免"这页能排那页不能"：

| 约定 | 实现 |
|---|---|
| 排序三态 | 点表头：**升序 → 降序 → 取消**（取消回到业务默认顺序）。`aria-sort` 与 `⇅/▲/▼` 同步 |
| 排序在哪做 | `ui/dom.js` 的 `sortRows(rows, sort, getter)`，页面只提供取值函数；`table()` 仍是**纯渲染**，不碰数据 |
| 比较规则 | 数字按数值比；日期与编码按字符串比（ISO 日期天然有序）；其余 `localeCompare('zh-CN')`；空值统一排最后（升序降序都排最后，不因空值打乱视线） |
| 筛选在哪做 | 页面模块状态（如 `bomFilter` / `routingFilter` / `state.filter`），**不改库、不改数据**；下拉项从当前库动态生成 |
| 计数提示 | 筛选后显示"显示 N / M 条 + 重置"，避免以为数据丢了 |
| 校验不看筛选 | 排程页的约束检查始终跑**全量任务**，筛选只影响展示 —— 否则"筛掉违规任务"就成了"没有违规" |

本轮新增/补齐的筛选：

- **BOM 明细**：按产品、层级、母项三个维度筛选（母项下拉标注成品/半成品，半成品带徽标），可叠加。
- **工艺路线**：按产品、工序名称筛选。
- **生产订单**：全部列可排序（订单号默认降序，最新在前）。
- **排程计划表**：订单 / 工序 / 工作中心 / 状态 / 日期区间五维筛选 + 全列排序。
- **物料页各表**：齐套明细、库存、到货、需求均可排序。

术语统一：BOM 里的"父项"全部改为**"母项"**（与"子项"成对，避免与"父/子订单"混淆）。

#### 3.6 排程页：当日计划与约束说明

**当日计划查询**（独立卡片）：选一个日期（或点「今天」），列出当天要做的工序 ——
工序名 / 工作中心 / 当日数量 / 计划区间 / 状态，底部汇总"N 道工序 · 合计 X 件"。
它回答的是 PMC 每天早上的第一句话："今天干什么、在哪个中心、多少件。"
与上方甘特/计划表是**两个视图**，同一份 `tasks` 数据：计划表看"整单进度"，当日查询看"某天的活"。

**约束规则说明表**（折叠区）：每条硬/软约束展开为一行，六个字段：

| 字段 | 内容 | 为什么需要 |
|---|---|---|
| 编号 | `HC-01` / `SC-03` | 便于沟通时指代 |
| 级别 | 硬（拦截）/ 软（提示） | 决定"能不能确认计划" |
| 规则 | 一句话规则 | 说清是什么 |
| 判定口径 | 具体怎么算（如"按 (工作中心, 日期) 汇总需求量与可用工时比较"） | 避免"为什么算我超产能"的争论 |
| 命中影响 | 命中后会发生什么（拦截确认 / 仅提示） | 说清后果 |
| 怎么改 | 具体动作（调日期、换中心、补工时、先做上游） | 让提示可执行，而不是只报错 |
| **命中数** | 当前计划下该条命中的条数 | 让"规则表"变成"体检报告"，不是说明书 |

数据来源是 `core/constants.js` 里 `HARD_CONSTRAINTS` / `SOFT_CONSTRAINTS` 的 `basis` / `effect` / `fix` 字段 ——
约束的定义与解释放在同一处，不会出现"代码改了、说明没改"。

**执行（§4.5）**
- 开工先过 G1（物料可支撑量）与 G2（上游已合格且未流转量）；完工申报受 G3 约束。
- 数量勾稽：订单已开工 = 首道工序累计开工；订单合格完成 = 末道工序累计合格。
- 所有申报都写入**报工履历（只增不改）**，页面底部可查，用于追溯与对账；
  因缺料被拒绝的开工尝试也会记入停工记录，供"缺料停工次数"指标使用。

**口径（§4.10）**
- 12 项指标在 `core/metrics.js` 里集中定义，每项都带 `formula`（公式）、`basis`（口径）、
  `detail`（明细），统计分析页可下钻。
- 仪表盘与统计分析共用 `defaultPeriod()`，避免同名指标出现两个数字。
- 分母为 0 时显示 `—` 而不是 `0.0%`（0.0% 会被读成"实际为 0"，真相是"没有样本"）。

#### 3.7 异常明细不许为空

异常中心有个硬性要求：**数量字段有值，明细就必须能展示**。"预计到货延期 3 项"点进去却是空白，
用户除了不信任这个数字，什么也做不了。此前 `MAT_INBOUND_DELAY` 就出现过这种空明细，根因是
订单 `planStart` 为空时也在生成异常。现在：

- `MAT_INBOUND_DELAY` **仅在该订单存在"有达需日、且达需日晚于开工日"的物料行时**才生成；
- 未排产订单（无 `planStart`）不产生"预计到货延期"（没有开工日，就无所谓"晚于开工"）；
- `detail` 至少包含：物料编码+名称、需求量、库存、累计达需日、晚几天；
- `MAT_SHORT` / `MAT_QTY_SHORT` 的 `reason` 与 `detail` 同样写明"库存多少、已确认到货多少"，
  让人一眼看出还差多少、缺在哪个环节；
- 回归测试直接断言"**任何异常的 `detail` 都非空**"，不针对某一条规则 —— 以后新增异常类型也不会漏。

## 4. 需要在验收时确认的两处口径解读

实现过程中发现方案原文存在两种读法，代码按下列解读实现，**并在界面口径说明里写明**，
请评审时确认或改判：

1. **准时完工率分母（D-03）**：原文"当期应交订单（含未完工）"。
   实现为"**应完工日已到期**（≤ 基准日）且落在统计期内的订单，含已到期未完工"。
   理由：未到期订单尚未构成"应交"，若计入分母，任何未来订单都会被预先算成未准时，
   指标会长期失真（实测可低至 5%）。
2. **部分齐套是否计入缺料**：`缺料订单数` 只统计"缺料"状态，部分齐套不计入，
   但会以"部分齐套"状态出现在物料页与异常中心。

## 5. 数据入口、场景与持久化

### 5.1 内置演示场景

| 场景 | 销售订单 / 生产订单 | 用途 |
|---|---|---|
| 简单 | 6 / 7 | 物料齐套、每工序单一工作中心，用于演示主流程 |
| 中等（默认） | 25 / 27 | 部分缺料、多工序、负荷接近上限 |
| 复杂 | 80 / 84 | 订单集中、到货延期、部分开工、替代中心、多异常并发 |

- 演示数据用固定种子生成，同一场景每次重建结果**逐字节一致**；生产订单同时包含
  "多对一（多行合并）"与"一拆多（拆批）"两种形态。
- 数据版本号 `SEED_REV` 写在数据里。若浏览器里存的是旧版本演示数据，
  顶栏会出现提示条，可一键重建，避免"半新半旧"数据导致数字看着不对。
- 该提示条**只对内置场景数据生效**（`seedRev` 非空且与当前版本不一致）；
  导入的外部数据不会被误判为旧数据，也就不会被"重建演示数据"误覆盖。

### 5.2 导入 Excel / CSV（推荐：合并，不清空）

**入口**：顶栏「导入」或基础数据页的「导入文件」。两者都打开同一个批量导入弹窗，
可一次选择多份文件；从基础数据页进入时会带上当前下拉选中的场景作为默认值。

**支持的文件**

| 格式 | 说明 |
|---|---|
| `.xlsx` | 浏览器原生解压 + 解析 XML，不依赖任何第三方库；支持共享字符串、内联字符串、多工作表 |
| `.xls` | Excel 97-2003（BIFF8）：自实现 OLE2 复合文档 + BIFF 记录解析，支持共享字符串跨 `CONTINUE` 分块 |
| `.csv` / `.txt` | 自动识别编码（UTF-8 / 带 BOM / UTF-16 / GBK-GB18030）与分隔符（逗号 / 分号 / 制表符） |

**一次导入多份、自动识别场景**
按工作表名、文件名、表头内容综合判断属于哪类数据（产品 / 物料 / BOM / 工作中心 / 工序适配 /
库存 / 到货 / 销售订单行 / 生产订单），识别结果可在预览表里逐份改成正确场景。
处理顺序按依赖固定为：产品、物料、工作中心 → BOM、工序适配、库存、到货、销售订单行 → 生产订单；
即使选择顺序颠倒，也能在同一批里"产品 + 销售订单 + 生产订单"一起导入。

**合并语义（不会误覆盖）**

| 数据类型 | 判重键 | 已存在时的行为 | 影响范围 |
|---|---|---|---|
| 产品 / 物料 / 工作中心 | 编码 | 覆盖更新，**保留原 id** | 只改本集合 |
| BOM 明细 | 产品 + 层级 + 子项 | 覆盖更新，不产生重复行 | 只改 BOM |
| 工序与工作中心适配 | 工作中心 + 工序名 | 覆盖更新 | 只改适配表 |
| 库存 | 物料 + 仓库 | 覆盖数量 | 只改库存 |
| 采购到货 | 物料 + 预计到货日 + 数量 | **跳过**（单据不覆盖） | 只改到货 |
| 销售订单行 | 销售订单行号 | **跳过**（单据不覆盖） | 只追加订单行，订单头按单号合并 |
| 生产订单 | 生产订单号 | **跳过**（单据不覆盖） | 只追加生产订单 |

- 因此"先导销售订单、再导生产订单"与"先导生产订单、再导销售订单"都不会互相覆盖；
  同一份文件重复导入是幂等的（主数据更新、单据跳过），不会堆出重复行。
- 生产订单允许只给「产品编号」而不填「销售订单行号」：系统会补一条占位销售行
  （单号 `SO-AUTO-<生产订单号>`，`auto: true`），让"单独导入生产订单"可用；
  若给的是不存在的销售行号，则整份文件报错并提示先导销售订单。

**表头与取值宽容**

- 表头可以在前 10 行内（真实报表常有"XX 数据（2026 版）"标题行）；
- 支持中英文别名（如 `产品编码` / `Item Code` / `productCode`），按别名识别时会在结果里提示；
- 数字容忍千分位；日期支持 `2026-12-01`、`2026/12/1`、`20261201` 与 Excel 日期序列号；
- 枚举容忍中文写法（`原材料`→`RAW`、`标准工时`→`STD_HOURS`），转换会在提示里写明。

**表头识别的实现与边界**

识别分两步，都不是"AI 猜测"，而是**确定性的别名匹配 + 打分**，因此结果可复现、可解释：

1. `locateHeader()`：在前 10 行内逐行尝试，把每行的单元格与 9 类场景的**别名表**比对，
   取"命中列数 ×2 + 命中必填列 ×4 + 必填覆盖率 ×6"最高的一行作为表头行。
   表头单元格会先归一化：去首尾与全角空格、去末尾括号说明（`数量（件）`→`数量`）、
   去必填标记（`产品编号(必填)`→`产品编号`）、统一大小写与 `_` / 空格差异。
2. `detectSpec()`：对 9 类场景各跑一遍上一步，取总分最高者；文件名或工作表名命中场景关键词再 +10。
   若最高分与第二名差距 ≤3，或只有 1 列命中（信息量不足），则**不自动选**，在预览表里留空并给出
   候选建议，由用户下拉确认 —— 猜错场景会按错误规格校验，报一堆莫名其妙的"缺必填列"，比让用户点一下更糟。

别名表覆盖的写法举例：`产品编码` / `产品编号` / `Item Code` / `productCode` / `料号`；
`客户要求完工日` / `要求完工日` / `交期` / `dueDate`；`数量` / `计划数量` / `qty`。

识别不了的情况只有三类，界面上会分别给出**不同**的说明，而不是统一一句"无法识别"：

| 现象 | 实际原因 | 界面提示 |
|---|---|---|
| 预览里行数为 0 | 读到了文件，但表头没命中任何别名（多见于自定义列名） | 「识别到 0 行 · 表头第 N 行」+ 读取到的前几列表头原文 |
| 行数正常但场景为"待指定" | 只命中 1 列或两类场景分差过小 | 列出候选场景与分数，提示手动选择 |
| 整份读取失败 | 文件损坏 / 加密 / 不是真正的 xlsx | 显示解析层的具体错误（如"不是有效的 xlsx 文件"） |

> 需要 AI 参与吗？不需要。表头识别是**枚举匹配**问题，规则化实现比模型更稳、更快、可解释，
> 也不引入联网依赖（这与"零依赖静态站"的定位一致）。AI 在本项目里只出现在异常分析页的降级占位。

**失败姿态**
每份文件独立成败：某份有错误只跳过该份，其余照常导入；错误给出**Excel 行号 + 字段 + 原因**
（如 `第 5 行 · 客户要求完工日：日期无法识别`）。校验阶段在库的副本上做，全部通过后才写库，
不会出现"一半新一半旧"。

**可追溯**
每条导入记录写入 `imp = { batch, file, at }`；批次汇总追加到 `importLogs`（保留最近 50 批），
在「场景 → 数据管理 → 导入履历」可查批次号、时间、文件、新增 / 更新 / 跳过条数。
导入弹窗默认勾选"导入前自动导出当前数据备份"。

**模板**
弹窗内可下载 9 类场景的空白模板（CSV，Excel 可直接打开填写），也可一次下载全部。

### 5.3 载入整库 JSON（替换全部数据）

用于测试数据集整体载入或备份还原，入口在「场景 → 数据管理」。

| 规则 | 说明 |
|---|---|
| 必填集合 | `productionOrders`（数组，可为 `[]` 表示只导入主数据） |
| 可选集合 | `products` / `materials` / `bomItems` / `routings` / `routingOps` / `workCenters` / `capabilities` / `downtimes` / `inventory` / `inbounds` / `salesOrders` / `salesOrderLines` / `orderLinks` / `planVersions` / `tasks` / `actuals` / `shipments` / `exceptions` / `freezeLogs` / `blockedLog` / `importLogs`；缺省补空数组 |
| 顶层信封 | 直接放数据集对象，或包在 `data` / `dataset` / `db` 里（兼容自身备份文件） |
| 编码解析 | `productCode` / `orderCode` / `workCenterCode` / `materialCode` / `versionCode` 自动解析成 id |
| 版本重连 | 缺 `planVersions` 时自动建 `PV-IMPORT`；`activeVersionId` 失效时自动修正；脱链任务改挂工作版本 |
| 校验粒度 | 必填、枚举、数字、日期（含 2 月 30 日这类"格式对但不存在"）、编号重复、关联存在性；错误给 `集合[下标].字段` |
| 失败姿态 | **任一条错误即整批不载入**，弹窗列出前 8 条并显示总数 |
| 覆盖行为 | **整库替换**：未出现在文件里的集合会变成空数组。只想增量补充数据时请用 §5.2 |

### 5.4 清空全部数据

- 入口：「场景 → 数据管理 → 危险操作」。
- 二次确认：必须先输入「清空」二字，按钮才可用；默认勾选"清空前导出 JSON 备份"。
- 清空后写入一个空库（而不是只删 storage 键），因此**下次打开不会自动重建演示数据**；
  顶栏出现"当前数据库为空"提示条，可直接导入 Excel/CSV 或载入演示场景。
- 空库下 10 个页面均可正常渲染（指标显示 `—` 而不是 `NaN`）。

### 5.5 数据归属与手工录入

- 所有数据保存在 `localStorage` 单键 `ppd-mvp-v1`，按"协议 + 主机 + 端口 + 浏览器 Profile"隔离。
- 手工录入（基础数据页「新增」、执行页报工、派工调整等）与导入数据写在**同一集合**里；
  合并导入只增改本文件涉及的记录，**不删除、不清空**其他记录，因此手工数据会保留。
- 主数据按编码更新时保留原 `id`，已引用该产品的生产订单、BOM、库存不会脱链。
- 需要"整体回到某个时点"时用 JSON 备份：备份/恢复是整库替换，与合并导入是两条不同的通道。

### 5.6 与 ERP / WMS 的对接现状

**当前只做文件级对接，没有系统集成**：

| 能力 | 现状 |
|---|---|
| 从 ERP 取数 | 导出 Excel/CSV 后导入（本版支持 xlsx / xls / GBK-CSV） |
| 向 ERP 回写 | 只提供导出：基础数据「导出当前表」、整库 JSON 备份；没有单据状态回写 |
| WMS 库存同步 | 通过库存模板 / 库存表导入，按（物料 + 仓库）覆盖数量；无实时接口 |
| 接口 / 账号 / 鉴权 | 无。当前是单用户本机应用，没有服务端与登录 |
| 扩展点 | 所有字段映射集中在 `io.js` 的 `IMPORT_SPECS`；要做 API 直连，在 `core/` 增加 adapter 复用同一套校验与合并函数，页面无需改动 |

因此，"连接 ERP/WMS"目前等价于"按模板导出 → 导入"，属于**批量、准实时**而非实时同步；
也没有增量水位、冲突检测与主数据版本管理。

**销售/生产分别导入互不覆盖**、重复导入幂等（主数据更新 / 单据跳过）、手工录入保留、
BOM 与库存自然键去重、清空后不重建演示数据且可重新导入。

解析兼容性侧覆盖（针对"别人的 Excel 打不开"这一类问题）：命名空间前缀写法（`<x:row>` / `<x:c>`）、
属性用单引号、`inlineStr` 无 `sharedStrings`、`sharedStrings` 富文本 `runs`、单元格缺 `r` 属性、
关系文件里写绝对路径 target、工作表读写流（write-only）产物、合并单元格、表头带单位括号与必填标记、
表头落在第 6 行、只有一列信息的表头不硬猜场景、空工作表不报错。

数据集导入侧覆盖：四种顶层信封、必填集合缺失与非数组集合的拒绝、字段级错误定位
（数量 / 枚举 / 日期含非法日历日 / 重复编号 / 关联不存在）、编码→id 解析、
**脱链任务重挂工作版本**（回归：修复前排程页可见 0 条）、缺版本时自动建版本、
失效 `activeVersionId` 修正、与备份格式互导、导入后直接排产与 12 项指标无 NaN。

业务规则侧覆盖（`tests/rules.test.mjs`，34 项）：以 TA-PO-001~008 八张订单逐条钉住齐套口径 ——
分批到货时要按日累计才能达需（001）、库存即够时齐套日为空（002）、库存与到货要合并累计（003）、
单批晚于开工即到货风险（004）、恰好等于需求算齐套（005）、无库存无到货时齐套日不可知（006）、
分批累计仍早于开工（007）、首批够但第二批才达需（008）；另覆盖整单齐套日取缺料物料**最晚**值
（给 001 再加一个更晚达需的物料，齐套日必须从 +5 变 +9）、`materialReadyDate` 与 `kittingOf` 结论同步、
**未排产不误判为到货风险**、**任何异常 `detail` 都非空**、`explodeBom` 不计有下级 BOM 的半成品但半成品库存仍可见、
`explodeBomTree` 保留半成品行并给出缩进/所属母项/换算需求量、导入生产订单同时写 `orderLinks`
（重复导入被拒绝且不重复建关联）、交期仍按 `salesOrderLineId` 回查。

> 这组用例首次运行是 18 通过 / 16 失败，全部集中在齐套状态。排查后确认**是夹具错了**：
> 八张订单共用同一个产品，而该产品 BOM 有 8 个物料，于是每张订单都"缺 7 个物料"，一律判缺料。
> 改成"一单一个产品 + 一对一 BOM"后 34 项全绿，实现代码未改一行。记在这里是因为它提醒一件事：
> **测试数据必须让"订单需要什么"显式可控**，否则测出的是假失败，容易误改正确的实现。
