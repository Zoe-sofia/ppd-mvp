## 0. 一页纸摘要

**本方案做了什么**

把 V1.0 从"产品提案"推进到"可评审、可执行、可验收"的层面，方式是：

1. 把 V1.0 的全部内容**锁定为范围基线**（不做任何修改、删减、重排）；
2. 识别基线中"只写到提及级、不足以支撑开发与验收"的空白处，以 **31 项补充** 填平；
3. 为每项补充标注 **边界 / 是否触及既有功能 / 依赖 / 优先级 / 所属阶段 / 交付物 / 验收方式**；
4. 为 V1.0 的六个阶段加上 **进入条件与退出条件（门禁）**，使阶段推进可判定；
5. 汇总 **14 项风险、10 条必要假设、12 项基线待确认事项（P01–P12）+ 10 项新增待确认事项（N-01–N-10）+ 8 处基线一致性观察（O-01–O-08）**。

**本方案没有做什么**

- 未新增任何业务模块、页面、数据实体或业务规则；
- 未修改 V1.0 的九大模块范围、24 条业务规则、六个阶段顺序、21 项范围外清单；
- 未做技术选型与架构决策（V1.0 §8.2 已给方向，实施阶段另行确认）；
- 未替业务方填死 P01–P12，只给出"默认假设 + 决策截止点"。

**补充项构成（31 项）**

| 类型 | 含义 | 数量 | P0 | P1 | P2 |
|---|---|---|---|---|---|
| T1 规格细则补充 | 把"提及级"描述补到"可判定、可测试"精度 | 13 | 5 | 8 | 0 |
| T2 口径统一 | 建立单一事实来源，消除页面间算法分歧 | 3 | 3 | 0 | 0 |
| T3 质量与验收工程 | 追溯、门禁、回归、数据、缺陷、性能、证据 | 7 | 2 | 3 | 2 |
| T4 交付与运行准备 | 交付物定义、环境、备份、上线、操作说明 | 5 | 0 | 5 | 0 |
| T5 治理与变更控制 | 范围锁定、决策留痕、双线管理载体 | 3 | 2 | 1 | 0 |
| **合计** | | **31** | **12** | **17** | **2** |

**三句话结论**

1. **范围健康**：V1.0 的模块划分、规则体系与阶段安排自洽，具备直接作为基线的前提；31 项补充全部为"规格、口径、验收、治理"性质，不扩张范围。
2. **最大阻塞不在功能，而在口径**：12 项 P0 中有 8 项是口径与判定规则（状态枚举、日期与数量口径、指标公式、齐套与可开工判定、约束判定、数量守恒、导入冲突）。口径不定，排产结果不可复现、验收无法判定——这是本项目最高优先级的工作。
3. **需要在本次评审拍板 6 件事**（见 §13），其中 P01/P02/P03 三项直接决定阶段二的开工条件。

## 1. 本方案的性质、范围声明与角色

### 1.1 性质

本方案是 V1.0 的**执行层文件**，不替代、不修订 V1.0。二者关系：

| 层级 | 文件 | 回答的问题 |
|---|---|---|

如二者表述冲突，**以 V1.0 为准**，并须通过变更登记（S-E01 / 附录 B）记录冲突点与裁决结果。

### 1.2 范围声明（本方案的自我约束）

| 约束 | 具体含义 |
|---|---|
| C-1 不修改 | 不改动 V1.0 任何已定义的功能、字段、状态、规则、流程与阶段顺序 |

## 2. 如何区分"现有能力"与"本次新增/补充"

这是本方案最重要的约定。为便于评审逐行核对，采用以下**五级标签**，全文统一使用：

| 标签 | 含义 | 是否改变 V1.0 | 是否需业务方确认 |
|---|---|---|---|
| **【基线】** | V1.0 原文已定义的功能、字段、规则、阶段 | 否 | 否，照做 |
| **【规格】** | V1.0 已定义该能力，但描述止于"提及级"，本方案补足判定条件与边界（T1） | 否，仅提高精度 | 需确认补充内容是否与业务实际相符 |
| **【口径】** | V1.0 明确要求统一但未给出公式/定义（如 §4.10 末句、§5 BR 留白）（T2） | 否，仅填空 | **必须**确认，属业务裁决 |
| **【工程】** | 为可验收、可回归、可交付而增设的管理性产物（T3/T4/T5） | 否 | 知会即可，R1 批准 |
| **【观察】** | 阅读 V1.0 时发现的内部不一致或未定义点，**登记但不处置**，提请澄清 | 否，不擅自修补 | **必须**澄清，否则影响验收判定 |

**判定口诀**：看它是否让系统多做一件业务上的事。会 → 不在本方案内（走变更）；不会，只是把已有的事说清楚、测清楚、交清楚 → 在本方案内。

### 3.3 阶段基线（§11.2）

六个阶段的名称、完成项、阶段验收**全部继承，不调整顺序、不移动归属**。本方案仅在每阶段内补充：进入条件、退出条件、本阶段需完成的补充项、回归范围、交付物（§8）。

### 3.4 范围护栏（V1.0 §10 的 21 项范围外清单）

作为**评审时的对照清单**使用：任何提案、任何补充项、任何"顺便做一下"的诉求，逐一对照 §10 表格；命中即拒，除非走变更登记并由 R1 签署。本方案不重复抄录该表，直接以 V1.0 §10 为唯一依据。

### 3.5 基线成熟度评估结论

- **可直接开发的部分**：数据结构方向（§8.1 的 25 个实体与 6 条预留原则）、导入校验清单（§4.9 的 10 项）、页面结构（§6 的 10 个页面）、范围外清单（§10）。
- **必须在阶段一、二之前补齐的部分**：状态枚举与日期/数量口径、齐套与可开工判定、优先级评分卡、约束判定清单。这五项不定，阶段二的排产结果无法验证，也无法向 PMC 解释。
- **可以后置的部分**：性能验证场景、证据包规范、AI 边界细化（阶段五前完成即可）。

### 5.1 T2 口径类（3 项，全部 P0，最先完成）

#### S-B02 状态枚举总表【口径】
- **基线现状**：V1.0 在 §4.2/§4.3/§4.5/§4.6/§4.7 分别提到"订单状态""物料齐套状态""工序状态""发货状态""处理状态"，但未给枚举值与流转规则。
- **补充什么**：为六类状态各建一张表——`状态编码 / 中文名 / 所属对象 / 允许的前置状态 / 允许的后置状态 / 是否终态 / 判定触发方（人工/系统）`。状态编码一经确定，全系统页面、筛选器、导入模板、指标计算一律引用同一编码（见 O-05）。
- **明确不做什么**：不新增状态；不改变既有语义（如"齐套/部分齐套/缺料/预计齐套/到货风险"五种齐套状态原样保留）；不设计审批流。
- **交付物**：状态枚举表（6 张）；状态流转图（文字化，可用列表表达）。
- **验收**：任意页面出现的状态下拉/标签，均可在此表找到唯一对应项；不存在同义不同名的状态；导入模板的状态列有完整合法值清单。

#### S-B03 日期与数量基础口径【口径】
- **基线现状**：V1.0 要求"计算排产日期时扣除非工作日"（§4.4.5）、"区分计划/预计/实际日期"（§4.6），但未定义：日期按自然日还是工作日计、延期天数如何取整、一个日期字段由谁在何时写入。
- **补充什么**：
  1. **日历口径**：系统基准日为自然日；**排产推进**按工作日历（扣周末/节假日/计划停机）；**延期天数**按自然日计算并在指标字典中注明（二者不得混用，须在界面标注）。
  2. **日期链**：每个日期字段标注 `填写方（PMC/系统推算）/ 写入时机（排产确认、执行录入、发货登记）/ 是否允许为空 / 与上下游字段的先后约束`。
  3. **数量口径**：明确"数量单位取整规则"（是否允许小数、按件取整方式）与"部分数量开工时，未开工部分的计划日期是否保留"。
- **明确不做什么**：不引入时区/多班次/跨日排产（V1.0 §4.4.1 已排除班次级）；不引入工作日历的多种版本并存。
- **交付物**：日期口径说明（1 页）；数量口径说明（1 页）；日期字段责任表。
- **验收**：§9.8 的"能正确识别延期订单"可被唯一复算；同一订单在"排程页/交付页/统计页"看到的延期天数一致。

#### S-B01 指标口径字典【口径】
- **基线现状**：§4.10 列出 4+4+4 共 12 项指标，并在末句明确要求"具体指标计算口径需要在实施前统一，不能在不同页面使用不同算法"。**这是 V1.0 明确授权本方案填补的空白。**
- **补充什么**：12 项指标逐项表格化——`指标名 / 分子 / 分母 / 统计对象粒度 / 统计时间窗 / 日期基准（计划 or 实际）/ 排除规则（取消单、模拟方案、未开工单是否计入）/ 展示精度 / 数据来源字段`。
  - 需特别裁决的三处（对应 P03）：① 准时完工率的分母是"当期应交订单"还是"当期实际完工订单"；② 平均延期天数是否计入已取消订单；③ 工作中心利用率的时间基准（日历日 vs 可用工作日）。
- **明确不做什么**：不新增指标（12 项以外一律不做）；不改指标名称与业务含义。
- **交付物**：指标口径字典（12 条）；口径裁决记录（3 处，由 R1 签署）。
- **验收**：任取一个统计数值，可追溯到具体业务记录清单；同一指标在工作台与统计页数值一致（§9.8 要求）。

### 5.2 T1 规格类（13 项：P0 五项在前，P1 八项在后）

#### S-A03 物料齐套状态判定阈值【规格｜P0】
- **基线现状**：§4.3 给出五种状态名称与"当前库存/已确认到货/未确认到货"三类口径，但未定义"部分齐套"与"预计齐套"的分界。
- **补充什么**：给出判定顺序与阈值：
  1. 若可用量 ≥ 需求量 → **齐套**；
  2. 若可用量 > 0 且 < 需求量，且缺口无已确认到货可覆盖 → **部分齐套**；
  3. 若可用量 = 0 → **缺料**；
  4. 若当前不足但已确认到货日期 ≤ 计划开工日可覆盖缺口 → **预计齐套**；
  5. 若已确认到货日期 > 计划开工日 → **到货风险**。
  同时定义"多物料订单的整单状态"取最差项（短板原则），并定义未确认到货仅进入风险计算、不进入状态判定。
- **明确不做什么**：不改五状态集合；不引入按工序的齐套判定（§4.3 已定订单级）；不做跨订单自动重分配（§4.3 已定）。
- **交付物**：判定规则表（5 状态 + 整单聚合规则 + 边界值处理）。
- **验收**：§9.2 七条验收项可逐条对应到本规则表的某一行；构造正例/反例各一组可通过。

#### S-A04 最大可开工数量计算规则【规格｜P0】
- **基线现状**：§4.3 给出示例（需 100 件、物料仅支持 60 件 → 最多开工 60 件），未定义多物料时的取法、共用物料的分摊、已确认预留的扣减顺序。
- **补充什么**：
  1. 单订单多物料时，最大可开工 = min(各物料可用量 ÷ 单位用量)，向下取整；
  2. 共用物料在多订单间的分配顺序：**按已确认预留优先，其次按订单优先级评分，最后按计划开工日先后**（顺序须写入规则表，不得隐式依赖）；
  3. 已确认预留从"其他订单可分配库存"扣除的时机与可逆性（订单取消/改期时如何回退）。
- **明确不做什么**：不做跨订单自动重新分配（§4.3 明确"提示影响，不自动执行"）；不做工序级物料绑定。
- **交付物**：可开工计算规则（含取整、分摊、扣减顺序、回退）。
- **验收**：§9.2"能计算最大可开工数量""确认预留后能正确减少其他订单可分配库存"两项可复算且结果唯一。

#### S-A06 硬/软约束判定清单与提示规范【规格｜P0】
- **基线现状**：§4.4.8 列出硬约束 5 条、软约束 5 条，并规定"硬约束不允许确认""软约束允许保存但须显示风险"，但每条约束缺乏判定条件与提示内容规范。
- **补充什么**：
  1. 为 10 条约束分配唯一编号（HC-01…HC-05，SC-01…SC-05）；
  2. 每条给出判定输入字段、比较关系、边界情形（相等是否算违反、跨日边界、数量为 0 的情形）；
  3. 提示规范：每条提示须包含"涉及对象 + 违反原因 + 影响后果 + 可查看的调整位置"四要素；
  4. 多约束同时命中时的展示顺序（硬先软后，同级按影响订单数排序）。
- **明确不做什么**：不新增约束类型（新增走变更登记）；不改动硬/软归属；不设计自动修复。
- **交付物**：约束判定表（10 条）+ 提示文案模板。
- **验收**：每条约束至少 1 正例 + 1 反例可通过；§9.4"能识别硬约束和软约束""硬约束冲突不能进入正式确认"可判定；同一方案重复检查结果一致。

#### S-A09 工序数量流转守恒与部分开工边界【规格｜P0】
- **基线现状**：§4.5 规定"下游不得超上游合格可流转数量""不良不得作为下游流转""支持部分开工"，但未定义各数量字段的勾稽等式。
- **补充什么**：
  1. 给出勾稽等式（订单级与工序级各一组），明确"已开工/已完成/待生产/剩余/合格/不良"六者关系；
  2. 定义"合格可流转数量" = 上游合格完成量 − 已流转下游量；
  3. 定义部分开工场景下：计划日期的保留规则、剩余数量重新排产是否需 PMC 确认（默认需确认）、未开工部分是否计入"计划达成率"分母；
  4. 定义不良数量的隔离存放口径（不参与下游流转，但计入工序完成量与否需明确）。
- **明确不做什么**：不做报废/返工/返修流程（§4.5 已排除）；不做工序级质量判定。
- **交付物**：数量勾稽表（2 张）+ 边界情形清单（≥8 条）。
- **验收**：§9.5 六条验收项逐条可验证；人为构造超量流转数据必被拒绝；订单级与工序级汇总值始终一致。

#### S-A13 Excel 导入冲突处理策略矩阵【规格｜P0】

- **不做什么**：不改 10 项校验的既有权衡（"错误数据不得进入排产"为铁律）；不做批量删除。
- **交付物 / 验收**：处置矩阵 + 结果留存字段表；验收＝§9.1 五条通过；构造含重复行/非法关联的模板可得到行级错误反馈且核心数据未被污染。

## 7. 依赖关系与关键路径

### 7.1 依赖类型

| 类型 | 含义 | 表现 |
|---|---|---|
| D-数据 | 补充项依赖某类基础数据的结构或取值确定 | 如 S-A04 依赖 S-B03 的数量口径 |
| D-规则 | 某一判定依赖另一判定的结果 | 如 S-A03 齐套判定依赖 S-A04 可开工计算中的可用量口径 |
| D-时序 | 只能在某阶段之后进行 | 如 S-C06 性能验证必须在阶段六 |
| D-决策 | 阻塞在业务裁决上 | 如 S-B01 阻塞在 P03 指标口径 |

### 7.2 关键依赖链（三条主干）

**链 1（口径主干，决定阶段二能否开工）**
`S-B03 日期与数量口径` → `S-B02 状态枚举` → `S-A04 最大可开工` → `S-A03 齐套判定` → `S-A06 约束判定` → 阶段二排产可验证
> 说明：这条链上任一环未定，阶段二的排产结果就无法判断对错，只能"看起来像"。

**链 2（可解释性主干，决定阶段三能否通过）**
`S-A02 优先级评分卡` → `S-A05 工作中心推荐` → `S-A06 约束判定` → `S-A08 版本与模拟` → `S-A07 冻结` → 阶段三
> 说明：§9.3 要求"能展示排产评分依据"，§9.4 要求"硬约束不能进入确认"，二者都以 A02/A06 为前提。

**链 3（闭环主干，决定阶段四、五能否收口）**

> 说明：异常识别依赖数量与日期的偏差计算，偏差口径不定则异常无法自动触发。

## 10. 验收标准体系

### 10.1 三级验收

| 级别 | 对象 | 判定依据 | 判定人 |
|---|---|---|---|
| L1 模块验收 | 九大模块各自 | 模块卡 + §9 对应分节 | R4，R3 提交证据 |
| L2 阶段门禁验收 | 六阶段 | §8.2 的退出条件（每阶段 4~7 条） | R1 签署 + R4 复核 |
| L3 端到端业务验收 | 全系统 | §13 最终验收原则那条主线 + §9 八组验收全通过 | R1 + PMC 代表 |

### 10.2 验收判定规则

| 判定 | 条件 | 后续动作 |
|---|---|---|
| 通过 | 全部条件满足，P0 缺陷为 0 | 进入下一阶段 |
| 有条件通过 | 存在一般/轻微缺陷且不影响本阶段核心闭环；缺陷有明确修复计划与截止点 | 允许进入下一阶段，缺陷挂账并纳入下阶段回归范围；**挂账项不得跨两个阶段** |
| 不通过 | 存在阻断/严重缺陷，或任一硬性条件不满足 | 阶段内整改，重新提交验收；不得推进 |

**不可协商的红线（任一不满足即判不通过）**：
1. 硬约束冲突可被确认（违反 §4.4.8）；
2. 下游超量流转可被录入（违反 BR-11）；
3. 物料不足仍可开工（违反 §4.4.8 物料处理条款）；
4. 模拟方案影响正式计划（违反 BR-17）；
5. AI 直接修改正式计划、预留或执行记录（违反 BR-22）；
6. AI 不可用导致核心功能不可用（违反 §4.8 末段）；
7. 未校验的导入数据进入排产计算（违反 §4.9 末句）。

### 10.3 追溯机制

每项验收结论须能反向回答三个问题：**这条验收对应 V1.0 哪一条？对应哪条业务规则？由哪条用例证明？** 追溯矩阵（S-C01）的四列结构即为该机制的载体。评审时抽查任意 5 条结论，无法回溯即视为追溯失效。

### 10.4 不可直接验收项的替代验证

| 项目 | 为何难以直接验收 | 替代方式 |
|---|---|---|
| 排产"合理性" | V1.0 明确不承诺全局最优（§4.4.6） | 改为验收：约束满足性 + 结果可复现 + 评分依据可读 + 与 PMC 手工判断方向一致（抽样 10 例） |
| AI 输出质量 | 存在不确定性 | 改为验收：引用完整性 + 事实/推测标注 + 与系统数据矛盾时主动提示（§9.7）+ 可降级 |
| 甘特图"易用性" | 主观 | 改为验收：与表格数据一致性 + 修改同步 + 关键信息可见（不含主观评分） |
